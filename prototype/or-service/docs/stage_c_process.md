# Stage C：開發與求解過程

## 1. 本階段目標

把指派與路線轉為具有具體開始、完成、休息與返回時間的班次排程。保留使用者确认的 22 km/h 和座標直線距離，不增加道路倍率或交通緩衝。

本階段可調整人員指派與順序，不是只替 B 的路線貼上時間。初版只接受全新班次；遇到鎖定或進行中任務直接拒絕輸入，避免漏扣既有工時。

## 2. 輸入與準備

沿用 taipei_base.json：24 任務、6 人、20 車、12 地點；2026-10-12 台北時間 09:00–17:00。時間以相對 09:00 的分鐘表示。

- 人員需符合技能及工具需求。
- 最早開始、服務工時、軟期限來自任務欄位。
- 休息 30 分鐘須完整位於 12:00–14:00。
- 每位人員返回自己的出發點。
- COMPLETED 前置視為規劃開始前已完成；目前假資料全部 PENDING。

B 含移動的既有指派與路線作為部分 MIP start，只提供求解提示，不固定決策，也不宣稱既有路線一定能滿足 C。

## 3. 新增變數與限制

令 x 表示指派，u 表示未派，y 表示路徑弧，s/c 為開始／完成分鐘，l 為逾期，beta 為休息開始，z 表示在哪條弧出發前休息。

### 任務工時與開始時間

\[
c_i=s_i+p_i(1-u_i),\qquad 0\le s_i\le H(1-u_i)
\]

\[
u_i=0\Rightarrow s_i\ge r_i
\]

未派任務的開始、完成與逾期為 0；已派任務不能早於最早開始時間。

### 路線時間銜接

\[
\tau_{ij}=\frac{d_{ij}}{22}\times60
\]

\[
y_{ijk}=1\Rightarrow s_j\ge c_i+\tau_{ij}
\]

起點弧改用員工可開始時間；終點弧改用返回時間，且不得晚於班次結束。時間允許等待，等待會自然占用班次，不只檢查服務加移動的總和。

### 跨人員前置關係

\[
u_j=0\Rightarrow s_j\ge c_i\qquad (i,j)\in P
\]

清潔與複檢可以不同人執行，但複檢開始仍須等前置完工。已有指派前置限制也保留，禁止只派複檢。

### 休息

\[
180\le\beta_k,\qquad\beta_k+30\le300
\]

有路線的人選一條實際使用的弧，在出發前、當前地點休息：

\[
z_{ijk}\le y_{ijk},\qquad\sum_{(i,j)}z_{ijk}=h_k
\]

\[
z_{ijk}=1\Rightarrow\beta_k\ge c_i
\]

\[
z_{ijk}=1\Rightarrow s_j\ge\beta_k+30+\tau_{ij}
\]

起點與終點分別以可開始工作及返回時間代換。休息可在首件前、任務間或回程前，不能與服務或行駛重疊。沒有任務的人在出發點休息。

### 軟期限

\[
\ell_i\ge c_i-d_i,\qquad\ell_i\ge0
\]

資料期限全部為 soft，逾期不直接禁止指派，但列入目標與結果。技能、班次與前置則為硬限制。

## 4. 求解目標

Gurobi 多目標優先序：

1. 最小化 urgent 未派件數。
2. 最小化 high 未派件數。
3. 最小化全部未派件數。
4. 最小化加權逾期分鐘。
5. 最小化最大人員工時使用率（新增工作量分擔）。
6. 最小化完整閉合路線距離。
7. 在前述目標下盡量提早完成與返回，減少沒有必要的等待。

\[
F_4=\sum_i\omega_i\ell_i,\qquad
F_5=\sum_k\sum_{(i,j)}d_{ij}y_{ijk}
\]

逾期權重沿用 normal=1、high=3、urgent=10。第七層只作時間選解的最後平手判斷，不會優先於距離或期限。

已加入最大工時使用率平衡，詳見 `workload_balance.md`。尚未加入車輛停用時間或收益目標；這些是完整計畫中的後續選項，不能當成此次已實作。

## 5. 加入平衡前的執行紀錄（保留作比較）

執行命令：

```sh
python3 optimization/stage_c.py
python3 -m unittest discover -s tests -v
```

台北案例輸出：TIME_LIMIT，耗時 30.02 秒；24 件全部安排、0 未派；路線 83.037 公里，估計交通 226.5 分鐘；3 件逾期，總逾期 19.05 分鐘。

回呼記錄 81 次候選可行解事件與各目標階段結束時間，原始紀錄在 stage_c_schedule.json。階段結束不等於已證明最優；此次距離目標達到限時，最後的時間平手目標尚未完成，因此可能仍有可減少的等待。未提供各層界限，不虛構整體最佳化差距。

B 的總工時可放入班次，沒有保證期限與等待可行；C 新增這些條件，不能把兩份距離直接解讀為算法進步／退步。

## 6. 獨立驗證

結果檢查器從原始資料重算，不只讀模型自報：

- 指派唯一、技能工具、路線集合一致與總工時容量。
- 每段距離與移動分鐘、到場不得晚於開始、服務工時正確。
- 最早開始與跨人員前置關係。
- 休息長度、時間窗、與行駛／服務不重疊、位置可停留。
- 返回時間不得超過班次結束。
- 逐件重算逾期分鐘。

共 25 項測試通過，新增 5 項 C 測試涵蓋跨人員前置、release、實際休息、軟期限、晚釋放無法排入、錯誤結果拒絕與鎖定輸入拒絕。這是模擬條件下的模型驗證，不是企業實際工時或交通的驗證。

## 7. 交付檔案

- optimization/stage_c.py：模型、求解、結果檢查與報表。
- output/stage_c_schedule.json：完整精度時間與求解過程。
- output/stage_c_report.md：每人出發、到場、開始、完成、休息、回程、逾期與前置核對。
- tests/test_stage_c.py：本階段目標測試。

尚未建立 API、員工接單端、動態重排或搬車模型。
