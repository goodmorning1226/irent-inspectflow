# B：Gurobi 批次指派

本機授權已更新。台北案例已成功求解（OPTIMAL）：24 件全部指派、總起點距離約 98.019 公里；16 項測試通過，包含 4 組小型求解與窮舉最優結果比较。實際排程可行性留待 C 驗證。

## 與 A 的差別

A 每件任務独立推薦最近人員。B 共同分配全部待派任務，考慮每人總服務工時，可能把某件任務分給第二近的人，讓整體服務量與距離更好。

仍使用固定出發座標的大圓距離，不使用交通時間矩陣。清潔與複檢可一起指派，但 B 只保證前置也被安排，不計算前置完成時間。

## 模型

令 \(x_{ik}\) 為任務指派，\(u_i\) 為未派，\(E_{ik}\) 為技能及工具相容性，\(p_i\) 為工時，\(C_k\) 為班次扣休息的服務容量。

\[
\sum_k x_{ik}+u_i=1,\qquad x_{ik}\le E_{ik}
\]

\[
\sum_i p_i x_{ik}\le C_k=b_k-a_k-\delta_k
\]

前置任務尚未完成且同樣在本批次規劃時：

\[
u_j\ge u_i\qquad\forall(i,j)\in P
\]

若前置未完成且不在可規劃任務內，後續任務固定未派。

多目標優先序：urgent 未派件數 → high 未派件數 → 全部未派件數 → 總起點直線距離。

\[
\min\sum_{i,k}d_{ik}x_{ik}
\]

距離目標置於最後一層，不以少派任務換取更短距離。使用 Gurobi `setObjectiveN`，優先度為 40、30、20、10，各層目標退讓容忍值设為 0；限時及 MIPGap 仍可能使求解未證明最優。

## 執行

在 or-service 目錄：

```sh
python3 -m pip install -r requirements.txt
python3 optimization/stage_b.py
python3 -m unittest discover -s tests -v
```

預設輸出 `output/stage_b_assignments.json`。授權或求解失敗會回傳非零退出碼，輸出檔明確記錄 `has_solution: false`，不能當作派工計畫。

## 邊界與驗證

- 初版規劃全新班次的待派任務；鎖定或已指派任務保留、不參與最佳化，其占用工時尚未扣除，所以含既有工作負載的資料不能用此版判定剩餘容量。
- 未計交通占用、任務開始時間、休息位置與回程，容量只是服務工時上限，不保證可執行。
- 內建結果檢查器檢查重複指派、技能／工具、容量與前置是否安排。
- 7 項 B 測試驗證資料準備及結果檢查器，加上 4 項真實求解／窮舉比較與 5 項 A 測試，共 16 項通過。尚未驗證限時停止行為；A 與 B 的前置處理政策不同，不直接宣稱改善百分比。
- 台北案例與小型窮舉驗證已完成，結果見 `../output/stage_b_report.md`。後續依使用者指示進入 C。
