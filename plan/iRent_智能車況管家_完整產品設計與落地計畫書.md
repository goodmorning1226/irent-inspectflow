# **1 執行摘要**

產品的核心設計、價值與主要決策

iRent 智能車況管家將現行取還車照片上傳改造成導引式車況檢查。使用者完成車外前、後、左、右與車內前座、後座共六個區域，手機端即時判斷拍攝位置、距離、角度、模糊、曝光、反光與覆蓋率，條件合格後自動擷取影像。若發現疑似異常或局部資訊不足，系統才要求靠近該區域進行多角度補掃。

影像上傳後，雲端服務將本次影像與同車輛、同區域的歷史有效紀錄對齊，判斷是否出現新車損；車內影像則分類為髒污、普通與乾淨。系統將異常轉換成清潔、巡檢或維修任務，依安全風險、下一筆預約、區域需求、人員技能與移動時間完成優先排序及派工，完工後再次驗證車況，形成可追溯的營運閉環。

## **五項產品原則**

1.  正常使用者只需完成六區快速掃描，額外拍攝只在疑似異常、反光或資料不足時觸發。

2.  手機端處理低延遲品質檢查，較重的新舊車損比對在上傳後非同步執行，避免增加還車等待。

3.  AI 輸出必須包含位置、證據、信心與建議處置，不只輸出正常或異常。

4.  安全關鍵案件可立即暫停出租；責任歸屬、賠償與低信心案件保留人工決策。

5.  異常辨識、車輛狀態、派工、完工與重新上線形成同一條稽核軌跡。

# **2 問題定義與產品範圍**

## **現行流程的三個斷點**

| **斷點** | **問題**                                         | **後果**                                 |
| -------- | ------------------------------------------------ | ---------------------------------------- |
| 影像取得 | 使用者可能拍錯位置、過遠、模糊、反光或漏拍       | 後續辨識與責任判定缺乏可信證據           |
| 異常判斷 | 大量影像需人工查看，新傷、舊傷與髒污不易立即區分 | 預警延遲，客服與營運負擔增加             |
| 營運處理 | 異常通知與車輛下線、建單、派工及完工彼此分離     | 任務排序依賴人工，停駛時間與移動成本增加 |

## **目標角色**

| **角色**       | **主要需求**                                   | **產品提供的能力**                                     |
| -------------- | ---------------------------------------------- | ------------------------------------------------------ |
| 租車使用者     | 快速完成可用的取還車影像，不必反覆猜測是否拍對 | 六區引導、即時品質提示、自動擷取與局部補掃             |
| 後台營運人員   | 在同一處判斷車況、安排處理並確認索賠候選       | 前後影像比對、清潔／維修派工、嚴重度排序與人工索賠審查 |
| 清潔與維修人員 | 清楚知道哪台車、哪個位置及需要完成的工作       | 含異常位置與影像的任務、期限及後續完工回報依據         |

## **產品責任邊界**

- 產品負責取得可判讀影像、辨識車況、提出處置建議、建立任務、安排資源及驗證完工。

- 產品不自動決定事故法律責任與最終賠償金額；相關案件由授權人員依證據與公司政策判斷。

- 若歷史影像不足、視角不可比或模型信心過低，系統只建立待確認案件，不宣稱為本次新增損傷。

# **3 端到端服務流程**

| **階段**   | **處理內容**                                   | **主要輸出**                   |
| ---------- | ---------------------------------------------- | ------------------------------ |
| 1 建立檢查 | 依訂單、車號與車型建立 Inspection Session      | 六區清單與車型專屬拍攝規則     |
| 2 導引掃描 | 使用者完成車外四區與車內兩區                   | 每區合格影像與品質指標         |
| 3 即時防呆 | 檢查部位、距離、角度、模糊、曝光、反光與覆蓋率 | 單一明確調整提示或自動擷取     |
| 4 局部補掃 | 疑似異常或遮蔽時，取得中央、左側與右側視角     | 多角度近距離證據               |
| 5 雲端分析 | 前後影像對齊、新車損判斷、整潔度分類           | Finding、嚴重度、信心與證據    |
| 6 營運分流 | 規則與模型共同決定車輛狀態及任務               | 繼續出租、暫停、下線或人工覆核 |
| 7 智能派工 | 考慮預約、需求、人力、技能與路線               | 負責人、順序、ETA 與建議路線   |
| 8 完工驗證 | 整備人員拍攝相同區域，系統確認問題是否消除     | 關閉任務或退回補處理           |
| 9 重新上線 | 通過驗證並完成授權後更新車輛狀態               | READY 狀態與完整稽核紀錄       |

## **同步與非同步邏輯**

拍攝期間只執行需要即時反饋的品質與疑似異常檢查。合格影像上傳後，系統透過工作佇列執行前後影像比對與車內分類。使用者不必等待所有雲端模型完成；若後續判定屬安全或嚴重髒污，營運系統立即更新狀態並通知相關人員。

# **4 六區導引掃描設計**

## **現行 iRent 流程的嵌入位置與介面延續**

依 iRent 小學堂的取車認證、付款還車教學，以及官網取還車說明，車況影像不是獨立服務，而是既有取還車任務中的一個步驟。取車時，使用者先確認車輛外觀，異常時上傳照片並聯繫客服，之後才簽名確認取車；還車時，使用者記錄停車位置並拍攝車輛外觀，若有損傷再補充受損部位影像，之後繼續優惠、簽名、付款與鎖車等程序。InspectFlow 因此只替換影像取得元件，不重排整個取還車流程。

官方教學影片可辨識的手機介面，主要由「淺色車況／照片總覽頁」與「深色全螢幕相機頁」組成。總覽頁使用白色或淺灰背景、照片或車況區塊，以及底部紅色寬版主按鈕；相機頁則包含頂部返回與標題、中央預覽、底部照片縮圖列及大型圓形快門。正式產品延續這套版面與 iRent 紅色品牌操作，把照片格改成六區進度，把主操作改成「開始車況掃描」，並在相機頁以品質鎖定環和自動擷取取代每張手動按快門。疑似異常才展開近距離與多角度補掃；完成後回到原取還車流程。

| 現況拍照介面         | InspectFlow 替換內容               | 不改變的部分                 |
| -------------------- | ---------------------------------- | ---------------------------- |
| 車況照片總覽或照片格 | 六區掃描狀態、縮圖與待補掃提示     | 所在流程、車輛資訊與頁面導覽 |
| 拍照／新增照片       | 開始車況掃描                       | 底部紅色主要操作的位置與層級 |
| 大型快門             | 品質鎖定、自動擷取；另保留手動備援 | 全螢幕相機的操作心智         |
| 自由補拍損傷         | 由疑似異常框觸發近距離及多角度補掃 | 仍允許補充損傷證據           |
| 上傳／下一步         | 掃描摘要、上傳並返回原流程         | 後續簽名、付款與鎖車等程序   |

## **掃描狀態機**

| **狀態**        | **進入條件**           | **系統行為**                   |
| --------------- | ---------------------- | ------------------------------ |
| WAITING         | 進入指定區域           | 開啟相機並顯示車型專屬輪廓     |
| ALIGNING        | 偵測到目標車身或內裝   | 選出最優先的修正提示           |
| STABLE          | 品質條件連續多幀達標   | 鎖定曝光與焦點，開始短暫擷取   |
| CAPTURED        | 取得足夠合格幀         | 挑選最清晰且反光最低的影像     |
| DETAIL_REQUIRED | 疑似異常或局部不可判讀 | 框選區域並啟動近距離多視角流程 |
| UPLOADED        | 原圖與品質資料成功上傳 | 完成區域並前往下一區           |

**介面原則：**每個時點只顯示一項最重要的調整，例如「請再靠近」或「請向右移動」。當條件連續達標後自動擷取，避免使用者在對準後還需按快門而再次晃動。

# **5 即時影像品質與局部補掃**

| **檢查項目** | **判定方式**                           | **失敗處理**                   |
| ------------ | -------------------------------------- | ------------------------------ |
| 拍攝部位     | 車型、視角與部件分類模型               | 提示目前應拍攝的區域           |
| 距離         | 車身偵測框占比加單目深度估計           | 提示靠近或後退                 |
| 角度         | 車身關鍵點、透視比例與裝置姿態         | 提示向左、向右或降低手機       |
| 模糊         | Laplacian、動態模糊特徵與焦點狀態      | 提示保持穩定並重新對焦         |
| 曝光         | 整體與局部亮度、直方圖、暗部與高光比例 | 建議補光或更換方向             |
| 反光         | 高亮區域分割、局部資訊量與跨幀變化     | 框出受影響區域並引導改變角度   |
| 車牌         | 車牌偵測、OCR 與車號一致性             | 要求將車牌納入畫面或轉人工確認 |
| 覆蓋率       | 車身或內裝分割與必要部件可見度         | 指出尚未涵蓋的部分             |

## **多角度 Detail Scan**

6.  廣角畫面框出疑似異常、反光或不可判讀區域。

7.  使用者靠近，使目標落在中央掃描框，系統確認距離、清晰度與曝光。

8.  依序引導中央、左側、右側視角，每個視角擷取多幀並選取最佳影像。

9.  系統以視差、反光變化與表面紋理一致性判斷異常是否真實存在。

10. 證據仍不足時，保留低信心標記並送交人工覆核，不要求使用者無限重拍。

# **6 車損與整潔度 AI 設計**

## **外觀新車損判定**

| **步驟** | **功能**                                   | **候選技術**                               |
| -------- | ------------------------------------------ | ------------------------------------------ |
| 品質複核 | 去除重複幀，挑選清晰且反光較少的影像       | 品質評分模型與 OpenCV                      |
| 部件定位 | 定位門板、保桿、燈具、輪圈等部件           | YOLO Segmentation 或 Mask2Former 類模型    |
| 基準檢索 | 選取同車輛、同區域且視角相近的歷史有效影像 | Metadata 篩選與視覺特徵相似度              |
| 影像對齊 | 修正尺度、角度與局部透視差異               | DINOv2 特徵、LightGlue、RANSAC、Homography |
| 異常分割 | 定位刮痕、凹痕、裂痕、缺件與表面髒污       | 實例分割與多標籤分類                       |
| 前後比對 | 比較異常位置、形狀與範圍，判斷既有或新增   | Siamese 或時序差異模型加規則               |
| 證據融合 | 結合廣角、近拍與多視角結果                 | 信心校準、規則引擎與人工覆核               |

## **車內整潔度**

| **輸出** | **定義**                                   | **處置**                   |
| -------- | ------------------------------------------ | -------------------------- |
| 乾淨     | 無明顯垃圾或影響使用的污漬                 | 維持可出租                 |
| 普通     | 輕微灰塵或不影響下一位使用者的痕跡         | 保留紀錄，可依例行排程處理 |
| 髒污     | 垃圾、液體、食物、泥沙或明顯影響使用的情況 | 暫停出租並建立清潔任務     |

模型不只輸出整體分類，也應標註異常物件或區域及原因，避免營運人員只看到「髒污」卻不知道需準備何種清潔工具。

# **7 異常分流與車輛狀態**

| **案例**                                 | **風險** | **車輛狀態**         | **任務與通知**               |
| ---------------------------------------- | -------- | -------------------- | ---------------------------- |
| 燈具破裂、輪胎異常或其他影響行車安全項目 | P0       | 立即下線             | 維修或拖運；即時通知營運主管 |
| 大量垃圾、液體污漬或強烈影響下一位用戶   | P1       | 暫停出租             | 深度清潔；依下一筆預約升級   |
| 小範圍外觀刮痕且不影響安全               | P2       | 依政策維持上線       | 巡檢、記錄或集中維修         |
| 低信心或影像不可比                       | 待確認   | 依最壞風險暫停或維持 | 人工覆核，不自動歸責         |
| 普通或乾淨                               | 正常     | 維持上線             | 不建立即時任務或進入例行整備 |

## **狀態轉換控制**

- 只有授權服務或人員可以將車輛切換為 OFFLINE、TEMPORARILY_UNAVAILABLE 或 READY。

- 每次狀態變更都保存來源案件、原因、模型版本、操作者與時間。

- 高風險自動下線允許人工撤銷，但必須輸入理由並留下稽核紀錄。

- 重新上線需滿足任務完成、完工證據通過及營運規則三項條件。

| -------------- | ------------------------ | ----------------------------- |
| P0 安全異常    | 營運主管、維修調度與客服 | 未確認或無人接單即持續升級    |
| P1 髒污        | 區域營運與清潔人員       | 可能影響下一筆預約或逾時      |
| 低信心責任案件 | 客服或人工覆核小組       | 超過覆核 SLA 或使用者提出爭議 |
| 完工未通過     | 原處理人員與營運主管     | 第二次仍未通過時改派或升級    |

# **9 整備任務與完工閉環**

## **任務類型**

| **任務**   | **輸入**                             | **完成條件**                       |
| ---------- | ------------------------------------ | ---------------------------------- |
| 清潔       | 污漬類型、位置、面積、建議工具與期限 | 相同區域完工影像達到乾淨或普通標準 |
| 巡檢       | 疑似損傷位置、前後證據與檢查重點     | 人工確認類型、嚴重度及是否需維修   |
| 維修       | 部件、風險、可行駛狀態與站點需求     | 維修紀錄完成，必要安全檢查通過     |
| 清潔後複檢 | 車身過髒導致無法判斷的區域           | 清潔後重新執行車損辨識             |

## **整備人員流程**

11. 接收任務，查看位置、異常證據、所需工具、期限與下一筆預約。

12. 抵達現場並確認車輛，必要時回報找不到車或無法處理。

13. 開始任務後更新狀態，完成清潔、巡檢或維修。

14. 依原始異常區域的相同拍攝規則上傳完成影像。

15. AI 複檢通過後關閉任務；未通過則要求補處理或交由營運覆核。

16. 所有條件通過後，授權服務將車輛恢復為 READY。

# **10 智能優先排序與派工**

## **優先分數**

每筆任務 i 的優先分數綜合安全風險 Sᵢ、異常嚴重度 Rᵢ、下一筆預約急迫性 Bᵢ、區域供需缺口 Dᵢ與等待時間 Wᵢ：

Priorityᵢ = w₁Sᵢ + w₂Rᵢ + w₃Bᵢ + w₄Dᵢ + w₅Wᵢ

## **最佳化模型**

模型最小化總移動時間、車輛停駛時間、預約違約風險與 SLA 逾時成本。可使用 Vehicle Routing Problem with Time Windows，並加入技能、工具、班表、站點能力、任務先後關係與安全車輛不得出租等限制。

| **限制**   | **說明**                                               |
| ---------- | ------------------------------------------------------ |
| 人員時間   | 每位人員同一時間只能處理一項任務，且需符合班表與工時   |
| 技能與工具 | 深度清潔、巡檢、維修或拖運需由具備能力的人員或站點執行 |
| 任務期限   | P0、下一筆預約與 SLA 形成硬限制或高額逾時成本          |
| 任務相依   | 例如先清潔遮蔽污漬，再進行車損複檢                     |
| 車輛狀態   | 安全關鍵車輛在完成前不得被指派給新訂單                 |
| 動態事件   | 新增案件、交通時間變化或人員失聯時可重新排程           |

## **人工控制**

營運人員可鎖定任務、改派或調整期限；重新最佳化時不得覆蓋已開始、已鎖定或具合規限制的任務。系統應顯示改動對其他案件與預計完成時間的影響。

# **14 MLOps 與人工覆核**

## **模型生命週期**

17. 建立車型、區域、損傷類型、嚴重度、整潔度與不可判讀原因的標註規範。

18. 依車輛而非單張照片切分訓練、驗證與測試資料，避免同車影像洩漏造成高估。

19. 模型上線前進行離線評估、影子模式與小流量試點，再逐步提高自動化權限。

20. 持續監控車型、手機、光線、區域及季節造成的資料漂移。

21. 將人工覆核、完工結果與客訴案例回流，經資料品質審查後進入再訓練。

22. 每筆決策保存模型版本、門檻、輸入摘要與輸出，支援追溯及回滾。

## **人工覆核優先條件**

- 可能涉及責任歸屬或賠償，且模型信心未達高門檻。

- 安全關鍵損傷、影像不可比、歷史基準不足或多模型結果互相矛盾。

- 使用者提出爭議、營運人員覆寫結果或同車短期內重複出現異常。

## **監控指標**

| **類別**   | **指標**                                                |

| 品質模型   | 首次合格率、不可判讀率、平均補掃次數、各裝置失敗率      |
| 車損模型   | Recall、Precision、False Negative、既有誤判為新增的比例 |
| 整潔度模型 | 三分類混淆矩陣、髒污召回率、各類髒污表現                |
| 營運結果   | 人工覆寫率、任務退回率、完工未通過率、客訴後翻案率      |

# **18 主要風險與處理方案**

| **風險**             | **影響**                   | **處理方案**                                           |
| -------------------- | -------------------------- | ------------------------------------------------------ |
| 四個外觀視角仍有死角 | 可能漏掉車頂、底盤或遮蔽處 | 標準流程做快速初檢；事故、低信心或疑似區域啟動加強拍攝 |
| 反光或陰影造成誤報   | 增加補掃與不必要停駛       | 反光分割、多角度一致性、視角改變與人工覆核             |
| 歷史視角不一致       | 新舊判定不可靠             | 標準化拍攝、相似視角檢索、局部對齊；不可比時不自動歸責 |
| 車身髒污遮住損傷     | 清潔前無法判斷             | 建立清潔後複檢任務，保留待判定狀態                     |
| 車型與手機差異       | 品質門檻在部分裝置失效     | 車型規則、裝置監控、分層門檻與灰度發布                 |
| 模型錯誤下線         | 降低車輛利用率             | 信心門檻、受控自動化、人工撤銷、監控與快速回滾         |
| OR 無可行解          | 任務無法在期限與資源下完成 | 回傳違反原因，允許加班、外包、改派或延後預約等人工決策 |
| 企業系統資料延遲     | 預約與人員狀態不準確       | 事件版本、時間戳、冪等、過期資料警示與保守決策         |

## **產品完成定義**

產品完成並不等於模型可以辨識照片，而是從六區取得可信影像、產生可解釋的車況判定、更新車輛狀態、建立並安排任務，到完工驗證與重新上線均能穩定運作，且每一步都可追溯、可人工介入及可回滾。
