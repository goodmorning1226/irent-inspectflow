# iRent InspectFlow 手機端 Prototype 分階段實作計畫

最後更新：2026-10-10  
文件狀態：原第 8 階段已完成總驗證；全車連續掃描改造第 6 階段已完成自動、尺寸與視覺快照驗證，實際瀏覽器不中斷演練待人工補驗

## 全車連續掃描改造（2026-10-10 起）

新的掃描方式不再要求使用者逐一選擇六區，而是開啟一次橫向掃描鏡頭，由系統自動判斷是否拍到車、目前掃描區域及下一個建議區域。右下角將以六格汽車俯視圖顯示車頭、右側、左側、車尾、前座及後座的完成狀態；對準後的品質鎖定目標縮短為一秒內。

| 改造階段 | 實作主題 | 狀態 |
|---|---|---|
| 1 | 整次掃描狀態控制器、六區自動辨識狀態、下一區建議與防止重複完成 | 已完成 |
| 2 | 新掃描 HUD、右下角六區汽車圖、無車與下一區提示、一秒品質鎖定 | 已完成 |
| 3 | 單一連續影片與全車時間軸 | 已完成 |
| 4 | 同一鏡頭內的刮痕靠近及多角度補掃 | 已完成 |
| 5 | 車內前座、後座、污漬與六區完成流程 | 已完成 |
| 6 | 完整總驗證 | 已完成；瀏覽器實機演練待補驗 |

第 1 階段新增 `FullVehicleScanController`，固定建議順序為「右側 → 車頭 → 左側 → 車尾 → 前座 → 後座」，但控制器不強制使用者照順序掃描；只要系統辨識到尚未完成的區域即可鎖定並保存。控制器會把傳入的六區正規化為未開始，管理找車、區域追蹤、品質鎖定、區域完成、移動提示、異常補掃、進入車內與全數完成狀態。現有逐區介面尚未接上此控制器，會留到第 2 階段一起替換。

第 2 階段已將控制器接入既有掃描頁，並以新的全畫面 HUD 取代左側六區文字列與右側大型品質面板。右下角汽車俯視圖由 Flutter `CustomPainter` 繪製，車頭與車尾使用弧形區塊、左右側使用長形區塊、車內以兩個長方形區分前後座；灰色代表待掃描、青色代表目前辨識、綠色代表完成、青色外框代表下一區、橘色圓點代表異常。畫面會顯示未偵測到車、目前自動辨識區域及下一區提示；位置穩定後以 80 毫秒十段、總計 0.8 秒完成品質鎖定。此階段仍沿用原本單區影片與逐區入口，單一連續影片及取消逐區入口留到第 3 階段。

第 3 階段將車況總覽的主要操作收斂為單一「開始全車掃描」，不再要求使用者先選擇區域。新增 18 秒 `full_vehicle_scan.mp4` 及 `full_vehicle_scan.json`，由同一時間軸依序模擬右側、車頭、左側、車尾、前座及後座；每個事件會攜帶區域資料，驅動區域辨識、0.8 秒品質鎖定、自動擷取、移動提示及車內轉換。六區完成後一次回寫總覽。此階段的影片由現有本機車外及車內素材剪輯組成，尚未在連續主線中加入刮痕靠近或多角度補掃，留待第 4 階段。

第 4 階段把左側疑似刮痕直接接入同一段連續掃描。新版約 23.6 秒影片會在左側廣角框出疑似異常，引導使用者靠近，接著依中央、左側與右側三個視角自動保存補充影像，再退回廣角距離並繼續掃描車尾。全程不切換頁面，也不要求按快門；右下角車圖會保留左側異常標記。完成後左側摘要會標示已取得廣角與三個補充影像，並以中立文案等待後續處理。車內污漬仍留待第 5 階段。

第 5 階段完成車外轉車內與六區收尾。車尾完成後會先提示使用者開門，前座以座椅及腳踏區輪廓完成正常擷取，後座則在品質鎖定後框出右側座墊污漬並自動保存。右下角汽車圖會同時保留左側刮痕與後座污漬兩個異常標記；完成畫面及直向摘要以中立文案列出兩處待確認影像，本機輸出則同時包含刮痕與污漬 Finding。完整尺寸、重播、跳轉與展示演練留待第 6 階段總驗證。

第 6 階段已完成全專案靜態分析、24 項測試、六組尺寸矩陣、三種關鍵橫向 HUD 視覺快照、離線素材清點與 Web Debug Build。驗證期間修正完成狀態操作按鈕在 844×390 下繼承全寬 Theme 所造成的寬度限制。工作環境沒有可供 Agent 連線控制的瀏覽器工作階段，因此實際 Chrome 點擊、影片播放截圖及約 24 秒不中斷演練列為錄製前人工補驗；完整紀錄位於 `prototype/mobile/docs/stage6-continuous-scan-validation-report.md`。

第 6 階段後依最新展示需求再次收斂：六區總覽由全部待掃描開始，23.8 秒主影片改用右側、車頭、左側、車尾、前座與後座六個不同視角，並加入 0.8 秒滑動／淡化過場與 HUD 步行提示。取車檢查及完工複檢入口已移除，Prototype 僅保留還車車況檢查。六區完成後等待 0.9 秒即自動開啟摘要，不再要求按下完成；模擬上傳也移除固定失敗與重試流程。完成頁不提供「重設 Prototype」選項，只保留「返回 iRent 還車流程」，返回時直接準備下一次流程且不向使用者說明內部狀態重置。

最新入口頁依官方流程圖的基本元件改為「掃描／檢查車輛狀況」版型：保留返回、客服圖示與頂部紅色進度線，以車號、車型、`0 / 6` 及淺色六區俯視圖取代車輛示意圖與獨立六區卡片，底部主操作改為「掃描車輛狀況」。按下後直接進入橫向連續掃描，不再顯示六區總覽、橫放確認或即時掃描提醒。掃描時間軸中的每項新指令至少維持約 0.6 至 1.0 秒，同一動作橫跨相鄰事件時沿用相同文字，避免指令閃爍。

## 1. 實作範圍與執行規則

本計畫只處理 Flutter 手機端 Prototype。後台端與跨端串接必須等手機端完成第 8 階段總驗證、取得使用者確認後，再另外規劃及實作。

手機端仍追蹤車頭、左側、車尾、右側、前座及後座六區，但新版主線不再要求使用者逐區選擇。使用者只需啟動一次全車掃描，六區由時間軸模擬自動辨識與完成；掃描完成後仍可在總覽查看各區狀態與既有假資料摘要。左側刮痕、多角度補掃與後座污損皆已接入連續主線。

手機方向採「一般流程直向、掃描流程橫向」：車況總覽、區域選擇、摘要、上傳及完成頁維持直向；使用者進入車外、車內或完工複檢掃描前，先顯示橫放手機提示，接著將 M06 至 M14 與完工重掃畫面鎖定為橫向。離開掃描畫面後立即恢復直向。Flutter Web 無法可靠控制實體螢幕方向時，需以橫向瀏覽器視窗呈現相同版面。

執行時遵守以下規則：

1. 只能依序進行第 1 至第 8 階段，不提前實作後續功能。
2. 每個階段都要等使用者明確指示，例如「開始第 1 階段」，才可以開始修改程式。
3. 每個階段完成後立即停止，回報變更檔案、可操作成果、驗證命令、驗證結果及已知限制，等待下一次指示。
4. 第 1 至第 7 階段只做格式化及靜態分析；只有靜態分析無法涵蓋的關鍵資料邏輯，才追加一個最小目標測試。
5. 第 8 階段才執行手機端完整總驗證、視覺檢查與展示演練。
6. 所有 AI、影像品質與異常判讀結果都由假資料及時間軸腳本產生，畫面必須標示「Prototype 模擬結果」。
7. 實作階段不得建立後台專案、Mock API 或跨端通訊；手機輸出只需形成未來可供後台使用的本機 JSON 結果。

## 2. 驗證策略

### 2.1 每階段輕量驗證

第 1 至第 7 階段原則上只執行：

- `dart format`，格式化本階段異動的 Dart 檔案。
- `flutter analyze --no-pub`，確認沒有靜態分析錯誤。
- 只有 JSON 解析、狀態序列化等無法由靜態分析判斷的關鍵邏輯，才執行一個最小目標測試。

第 1 至第 7 階段不製作驗證截圖、不做人工流程檢查、不跑裝置尺寸矩陣，也不重複執行完整 Widget Test。這些檢查統一集中到第 8 階段；若某階段的程式尚未完整可操作，將限制記錄在回報中即可。

### 2.2 最終完整總驗證

第 8 階段一次完成：

- 全專案 `flutter analyze`。
- 全部 `flutter test`。
- 六區狀態、左側刮痕補掃、後座污損、上傳及完成返回的完整情境矩陣。
- 返回 iRent 流程、重播、影片結束及素材讀取失敗等重要操作。
- 至少三種手機尺寸的版面檢查，例如 360×800、390×844、430×932。
- 驗證直向總覽進入橫向掃描、離開掃描恢復直向的方向切換，並以對應的橫向尺寸 800×360、844×390、932×430 檢查掃描畫面。
- 離線執行與本機素材完整性檢查。
- Chrome 或可用 Flutter 裝置的完整展示演練；若 Android 工具鏈可用，再追加一次 Android Debug Build 或模擬器 Smoke Test。
- 依 3 分鐘影片預定路徑進行一次不中斷操作，記錄需要調整的等待時間。

## 6. 第 3 階段：共用影片掃描引擎與 Demo 控制器

## 9. 第 6 階段：後座車內污損掃描

**完成狀態：已於 2026-10-10 完成並通過階段輕量驗證。**

### 實作內容

- 加入 `interior_dirty` 影片、擷取影格及時間軸腳本。
- 從直向 M04 選擇後座後，經轉向提示進入橫向車內掃描版型。
- 導引框改為座椅與腳踏區輪廓，仍維持一次只顯示一項提示。
- 在指定時間框選飲料污漬、垃圾或遺留物中的一種主要異常。
- 形成車內 Finding，並將後座標記為已完成且待後續處理。
- 保持會員端文案中立，不顯示清潔費或責任判定。

### 輕量驗證

- 格式化異動檔案並執行 `flutter analyze --no-pub`；車內掃描流程與方向切換留到第 8 階段驗證。

### 完成門檻

後座可播放獨立車內素材、產生污損 Finding，且不誤用車外掃描輪廓。完成後停止並等待「開始第 7 階段」。

## 10. 第 7 階段：摘要、上傳、完成與完工複檢

**完成狀態：已於 2026-10-10 完成並通過階段輕量驗證及輸出 JSON 最小測試。**

### 實作內容

- 實作 M16 六區檢查摘要，整合固定完成區、左側結果與後座結果。
- 實作 M17 模擬上傳：逐項顯示整理進度並正常完成，不展示失敗或重試情境。

### 完成門檻

手機端可獨立完成車況選擇、掃描、補掃、摘要、上傳、完成及簡化完工複檢，並能產生穩定假資料供後台使用。完成後停止並等待「開始第 8 階段」。
