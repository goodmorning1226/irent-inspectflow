# iRent InspectFlow 產品提案概念說明

版本：V1.1  
更新日期：2026 年 10 月 14 日

## 一、產品定位

InspectFlow 是嵌入 iRent 既有取還車流程的「AI 智能車況檢查與整備管家」。它不另外建立一套租車服務，也不取代 iRent 原有的營運、清潔、維修或索賠系統，而是改善最前端的車況影像取得方式，並把影像整理成後台可以快速理解與處理的車況證據。

產品核心價值可概括為三件事：

1. **以掃描取代自由拍照**：在拍攝當下引導位置與方向，確保取得品質良好、區域完整且可比較的車況影像。
2. **以 AI 判斷差異並攔截異常**：比較本次取車前、還車後與可信歷史影像；疑似異常先暫停供租，不直接放行，交由人員確認。
3. **一次到位支援營運處理**：在同一工作台完成異常審核、車輛管理與清潔、維修、停用、索賠等請求送出，降低工作量與人工失誤。

目前 Prototype 已呈現手機端六區連續掃描，以及後台異常審核、處理中案件與車輛管理三個核心頁面。現階段的影片、判讀結果與 API 狀態為可重複展示的模擬資料；正式產品則會換成真實相機串流、AI 模型、雲端服務與企業 API。

## 二、目標客群

### 2.1 核心導入對象

InspectFlow 直接服務兩類使用者：進行取還車檢查的 iRent 服務使用者，以及負責車況審核與後續處理的後台客服及營運人員。產品需要同時降低前台掃描負擔，並協助後台在大量取還車事件中快速掌握車況與送出後續請求。

### 2.2 主要使用者

| 使用者 | 使用情境 | 核心需求 |
| --- | --- | --- |
| iRent 服務使用者 | 取車或還車時記錄車況 | 快速完成、知道怎麼掃描、避免漏拍與重拍，並留下可保障自身權益的紀錄 |
| 後台客服及營運人員 | 審核 AI 篩出的疑似異常、管理正常與處理中車輛 | 系統先排除正常事件並暫停疑似異常車輛，讓人員集中處理少量例外，在同一處完成車輛管理及清潔、維修、停用或索賠請求 |

### 2.3 協作與介接對象

清潔單位、合作維修廠、索賠承辦流程及 iRent 既有營運與索賠系統不是 InspectFlow 的直接使用者。營運人員在 InspectFlow 完成人工確認後，系統才以 API 傳送結構化請求，由既有系統承接人員、廠商、進度與後續作業。

## 三、痛點分析

### 3.1 租車使用者的痛點

- 現行自由拍照缺乏即時指引，使用者不確定是否拍對位置、距離與角度。
- 失焦、反光、過暗、遮擋或車身沒有完整入鏡，通常要到後續才發現照片無法使用。
- 需要逐張操作時容易漏拍，也會增加還車流程的負擔。
- 使用者雖然完成上傳，仍不知道影像是否足以保障自己的權益。

### 3.2 後台客服及營運人員的痛點

- 同一台車的照片分散在不同租程與時間點，人工尋找前後影像耗時。
- 不同使用者拍攝角度差異很大，難以判斷刮痕、凹陷或髒污是否為新增。
- 正常照片與疑似異常混在一起，營運人員需要觀看大量無問題影像。
- 車內髒污、車外髒污與車體損傷所需處置不同，但原始照片本身缺乏結構化分類。
- 判斷完成後，仍可能需要重新整理車號、位置、影像與處理原因，再輸入既有系統。
- 大量案件仰賴人員持續逐筆監看，容易因疲勞或交接產生遺漏，也難以安排較有彈性的值守與休息。

### 3.3 解決後的營運狀態

- AI 先篩出真正需要關注的疑似異常與低信心案件；只有高信心正常事件不進入人工審核清單，降低人員需要查看的案件數量。
- 疑似異常車輛先標記為暫停供租，避免在尚未確認前繼續被下一位使用者租用；人員確認為誤判後即可放行。
- 前後比較圖、異常特寫、車輛狀態與建議集中呈現，降低人工搜尋、判讀與資料轉錄造成的失誤。
- 清潔、維修、停用及索賠請求可從同一案件送出，人員不需在多個介面間反覆整理資料。
- 例外案件由系統集中排隊與標示急迫性，減少全天候逐張監看的負擔，讓排班、交接與休息更容易安排。

### 3.4 營運流程的痛點

- 影像取得、異常判斷、車輛狀態與後續處理之間缺少一致的資料鏈。
- 證據不足時容易陷入人工猜測，也增加客訴與責任判斷風險。
- 車輛可能因資訊不完整而被不必要地停用，或在異常尚未確認時繼續出租。
- 直接重做派工、維修或索賠系統成本高，也可能與企業現有流程衝突。

### 3.5 問題核心

真正的問題不只是「缺少一個車損辨識模型」，而是從拍攝開始就沒有形成穩定、可比較、可追溯的車況資料。InspectFlow 因此同時處理影像品質、前後比較、人工覆核及既有系統介接，而不是只提供單張照片的正常／異常答案。

## 四、解方設計

### 4.1 完整流程

整體流程維持簡單的七個階段：

1. **進入車況掃描**：使用者在原本 iRent 取還車流程中啟動車況檢查。
2. **完成六區掃描**：系統依序取得車頭、左側、車尾、右側、前座與後座影像。
3. **即時品質確認**：手機當下檢查位置、距離、清晰度、曝光、反光與完整度；不合格時只顯示一個最重要的調整指令。
4. **異常局部補掃**：廣角影像若出現疑似刮痕或髒污，才引導使用者靠近並取得異常特寫。
5. **雲端車況分析與攔截**：合格影像上傳後，系統比對本次取車前、還車後及必要的歷史基準；疑似異常或低信心案件先暫停供租並進入人工審核，只有高信心正常事件直接完成。
6. **營運人工覆核**：後台只顯示尚待確認的例外案件；營運人員可放行、送出清潔／維修／停用請求，或同步送出索賠請求。
7. **既有系統承接**：InspectFlow 以 API 傳送車況證據與處理方式，後續人員、廠商、排程與案件流程由 iRent 現有系統管理。

這個設計把「快速掃描」留給一般使用者，把較重的前後比對放在雲端，把責任與營運決策留給授權人員。

### 4.2 手機端設計

手機端延續 iRent 原有介面語彙，不新增獨立首頁。原本的拍照入口改為「掃描」，保留淺色頁面、紅色主要操作與清楚的車號資訊，降低使用者學習成本。

入口頁以六區車輛俯視圖呈現待掃描範圍。按下「掃描車輛狀況」後，畫面直接切換為橫向全螢幕掃描，不再經過額外說明頁。掃描期間以全畫面相機為主，只保留返回、簡短指令、品質框與右下角六區狀態圖，避免過多資訊遮住車輛。

互動原則包括：

- 一次只給一個明確動作，例如向左、向右、往前或保持穩定。
- 使用箭頭配合實際畫面移動，讓使用者不必閱讀複雜說明。
- 條件穩定後自動擷取，不要求再次按快門。
- 反光、失焦或位置錯誤在掃描當下排除，不送進後台成為假異常。
- 只有疑似異常才增加近距離補掃，正常車況維持快速完成。

### 4.3 手機端功能

- 六區連續車況掃描與完成狀態顯示。
- 車輛區域、距離、角度、清晰度與曝光品質提示。
- 向左、向右與往前等視覺箭頭引導。
- 畫面穩定後自動保存較佳影格。
- 疑似刮痕、凹陷、破裂或髒污區域框選。
- 異常特寫與不同觀察方向的補充影像。
- 車內前座、後座整潔狀況掃描。
- 六區摘要、上傳狀態及返回原 iRent 流程。
- 正式版可保留手動拍攝作為裝置或環境不適合自動掃描時的備援。

### 4.4 後台端設計

後台採單一營運工作台，不另外切換客服、派工、索賠或管理者情境。畫面只保留三個核心頁面，所有清單使用一致的 row 形式，點擊整列即可查看詳情。

#### 異常審核

只顯示尚未處理、尚未送入處理中或索賠流程的案件。清單呈現車號、偵測結果、異常位置、AI 分類、嚴重程度與車輛狀態；髒污會明確分成車內髒污與車外髒污。

詳情頁集中呈現六區影像、同車同區域的本次取車前／還車後比較、必要的歷史基準、異常特寫、AI 建議與車輛資訊。營運人員可：

- 送出索賠請求並同步處理。
- 確認異常並送出清潔、維修或單純停用請求。
- 判定為誤判並恢復正常狀態。

AI 只提供建議，最終營運決策仍由人員確認。

#### 處理中案件

集中顯示已送往外部系統的處理事件，包括車輛、處理類型、位置、急迫性與索賠請求狀態。詳情保留各區影像、異常特寫、車況比較及外部處理狀態。

尚未送出索賠請求的案件可在清單或詳情補送；已送出者會顯示鎖定狀態，避免重複提交。此頁只追蹤 API 請求與外部系統回傳，不假設清潔人員、維修廠商與排程如何分配。

#### 車輛管理

顯示目前正常的待租與租借中車輛，並提供車號、車型、位置、租用狀態與整潔狀態。待租車輛可直接：

- 送出清潔請求，案件移至處理中。
- 判定異常，車輛暫停供租並移至異常審核。

租借中的車輛維持資訊檢視，不允許直接進行營運處置。

### 4.5 後台端功能

- 待審異常依急迫性排序與搜尋。
- 同車同區域前後影像比較。
- 本次取車前與上次還車基準切換。
- 六區影像、異常位置與異常特寫檢視。
- 車內髒污、車外髒污與疑似車損分類。
- 放行、處理及索賠請求操作。
- 處理中案件與外部狀態追蹤。
- 防止重複送出索賠請求。
- 正常車輛狀態與整潔程度管理。
- 所有重要操作保留案件、時間、原因與操作者紀錄。

## 五、AI 應用方法

### 5.1 系統架構

系統可分成四個容易理解的部分：

| 層級 | 主要工作 |
| --- | --- |
| 手機 App | 顯示掃描引導，快速檢查影像品質，保存合格影格 |
| 雲端 AI 服務 | 比較前後影像，辨識疑似車損與髒污，整理證據與信心 |
| 營運工作台 | 呈現 AI 結果、影像比較與人工決策操作 |
| iRent 既有系統 | 接收處理或索賠請求，管理後續人員、廠商、進度與結果 |

手機端只執行需要立即回應的輕量判斷；較耗資源的影像對齊、前後比對與異常分析交給雲端。這樣可以兼顧掃描流暢度、模型更新彈性與不同手機的效能差異。

這裡較精確的說法是「手機端輕量視覺推論」，而不是籠統地宣稱所有 AI 都在邊緣裝置完成。位置、覆蓋率、模糊、曝光與反光等需要立即回饋的能力適合在手機端執行；跨租程影像檢索、影像對齊、異常辨識與多張證據整合則放在雲端。

### 5.2 資料流

```text
訂單與車輛資料
        ↓
手機六區掃描與即時品質檢查
        ↓
合格影像、區域、時間與品質資訊
        ↓
雲端選取可比較的取車前／還車後／歷史影像
        ↓
影像對齊、異常辨識與多張證據整合
        ↓
產生車況 Finding：位置、類型、嚴重度、信心與影像來源
        ↓
營運人員覆核
        ↓
放行，或透過 API 送出處理／索賠請求
        ↓
iRent 既有系統回傳處理狀態，更新車輛紀錄
```

每個結果都要能追溯到原始影像與使用的比較基準。若沒有足夠的可比影像，系統輸出「證據不足」，而不是直接認定為本次新增損傷。

### 5.3 模型使用

正式版可使用數個各自負責單一問題的模型，而不是期待一個模型完成所有判斷：

| AI 能力 | 用途 | 輸出 |
| --- | --- | --- |
| 區域辨識 | 確認目前拍到車頭、車側、車尾或車內 | 目前區域與是否拍對 |
| 影像品質判斷 | 檢查模糊、曝光、反光、遮擋與完整度 | 是否可用及調整方向 |
| 車身與內裝定位 | 找出車門、保桿、座椅等主要區域 | 可比較的部位範圍 |
| 影像配對與對齊 | 找到同車同區域的前後影像並修正角度差 | 可比較影像與可比程度 |
| 外觀異常辨識 | 尋找刮痕、凹陷、破裂等疑似問題 | 異常位置、類型與信心 |
| 整潔度辨識 | 辨識污漬、垃圾、遺留物與遮蔽 | 車內／車外髒污及位置 |
| 證據整合 | 合併廣角、異常特寫、歷史紀錄與規則 | 給營運人員的摘要與建議 |

AI 不直接決定法律責任、賠償金額或最終索賠結果。它的角色是減少人工搜尋與整理工作，並把不確定性清楚呈現給營運人員。

### 5.4 技術選型與目前實作

目前 Prototype 與正式產品應分開表述：

| 範圍 | 目前 Prototype 已使用 | 正式版建議設計 |
| --- | --- | --- |
| 手機端 | Flutter、本機預錄影像與時間軸 JSON | Flutter 串接相機串流；以傳統影像處理檢查模糊與曝光，以 TensorFlow Lite 或 Core ML 部署輕量模型辨識視角、車體範圍與遮擋 |
| 雲端判讀 | 固定腳本與預設 Finding | 影像特徵檢索與對齊、車體／內裝分割、損傷與整潔度辨識及證據整合服務 |
| 後台端 | React、TypeScript、Vite、Zustand 與固定假資料 | React 工作台串接帳號、案件、影像、權限、稽核與狀態 API |
| 系統介接 | 模擬 API 請求與跨頁狀態變化 | REST API 或企業既有介接規格，連接 iRent 營運與索賠系統 |

大型語言模型不是核心車況判讀模型。若未來採用，可用於整理人工可讀摘要或協助查詢，但車況位置、異常類型與信心仍應由可驗證的視覺模型、規則與原始影像支持。

### 5.5 資料使用與模型改善

官方提供的真實照片可以用來了解實際光線、車型、角度與使用者拍攝習慣，也能作為視角辨識與品質判斷的起始資料。不過原始上傳分類不一定等於照片真實內容，正式訓練前仍需清理、抽查與標註。

較適合的資料策略是：

- 先用既有照片建立車內／車外、區域與影像品質分類。
- 再由人工標註刮痕、凹陷、破裂與髒污的位置和類型。
- 將同一車輛的取車前、還車後與完工影像整理成可比較組合。
- 將人工覆核結果回存，持續修正模型容易誤判的情境。
- 訓練、驗證與測試需依車輛或租程分開，避免同一台車同時出現在不同資料集而高估成效。

## 六、獨特優勢與差異化

### 6.1 使用產品前的使用者流程

```text
進入取還車流程
→ 自行判斷要拍什麼
→ 逐張拍照與上傳
→ 不確定照片是否清楚或完整
→ 完成流程
→ 若後續有爭議，再由客服與營運人工查找照片
```

此流程的問題是品質檢查發生得太晚。照片即使已上傳，也可能因角度、反光或漏拍而無法支持後續判斷。

### 6.2 使用產品後的使用者流程

```text
進入原本取還車流程
→ 按下「掃描車輛狀況」
→ 依單一指令完成六區掃描
→ 系統即時排除不合格影像並自動擷取
→ 只有疑似異常才補拍異常特寫
→ 查看六區摘要並上傳
→ 返回原本取還車流程
```

使用者不需要理解 AI，也不必自行判斷每張照片是否合格；產品把複雜技術轉換為簡單的方向提示與完成狀態。

### 6.3 營運流程前後差異

| 面向 | 導入前 | 導入後 |
| --- | --- | --- |
| 影像品質 | 拍完才可能發現不可用 | 拍攝當下即時修正 |
| 影像範圍 | 角度與內容不一致 | 六區結構化掃描 |
| 異常查找 | 人工瀏覽大量照片 | AI 先篩出疑似異常 |
| 前後比較 | 人工搜尋不同租程影像 | 自動整理同車同區域基準 |
| 髒污處理 | 車內外問題可能混在一起 | 明確分成車內與車外髒污 |
| 決策依據 | 影像、車況與處理資料分散 | 同頁查看比較圖、特寫與建議 |
| 後續作業 | 人工重複輸入其他系統 | 以 API 傳送結構化請求 |
| 責任控制 | 可能過度依賴單張照片 | AI 整理證據，人工保留最終決策 |

### 6.4 主要差異化

1. **從影像源頭改善，而非只做事後辨識**  
   先確保照片可用，再進行車損判斷，降低「模型再好但輸入不可判讀」的問題。

2. **將掃描引導、AI 比對與營運處理串成同一流程**  
   不只回傳異常分數，而是形成可查看、可覆核、可送出的車況案件。

3. **優先比較同一租程的取車前與還車後**  
   比單純查看最近一張歷史照片更符合判斷車況變化的需求；歷史影像則作為補充基準。

4. **異常才增加操作成本**  
   正常車況維持六區快速掃描，只有疑似問題才要求靠近補掃，兼顧效率與證據完整性。

5. **人機協作而非完全自動定責**  
   AI 說明看到了什麼、依據哪些影像以及有多確定，責任與處置仍由授權人員決定。

6. **API-first，不重做 iRent 內部系統**  
   InspectFlow 專注於影像與決策證據，後續派工、廠商與索賠流程延續既有系統，可降低導入阻力。

## 七、預期效益

現階段尚未取得 iRent 的現況基準與正式試點結果，因此不宣稱固定改善百分比。預期效益應以試點前後數據驗證。

### 7.1 使用者體驗

- 降低不知道怎麼拍與反覆重拍的挫折。
- 縮短單區對準與確認所需時間。
- 提高一次完成率與六區完整率。
- 讓使用者知道已留下可判讀的車況紀錄，提升流程信任感。

建議指標：掃描完成時間、首次合格率、平均調整次數、流程放棄率及使用者滿意度。

### 7.2 車況判讀品質

- 提高影像清晰度、區域完整度與前後可比性。
- 降低反光、角度差異及漏拍造成的誤判。
- 將疑似車損、車內髒污與車外髒污轉為結構化紀錄。
- 對證據不足案件明確分流，降低過度判定風險。

建議指標：可判讀率、不可比率、異常召回率、誤報率、人工推翻率及補件率。

### 7.3 營運效率

- 減少營運人員瀏覽正常影像與搜尋歷史照片的時間。
- 縮短從異常發現到送出處理請求的時間。
- 減少在不同系統間重複整理車號、位置與影像證據。
- 讓處理與索賠請求具有一致的資料格式與追蹤紀錄。

建議指標：單案人工審核時間、每日可處理案件量、異常至送出請求時間及人工操作步驟數。

### 7.4 車隊與風險管理

- 更快隔離確實需要處理的車輛。
- 降低正常車輛因資訊不足而長時間停用的情況。
- 提高新舊異常與責任判斷所需證據的完整度。
- 建立可追溯的車況時間軸，支援未來維修、清潔與車型品質分析。

建議指標：平均停用時間、誤停用比例、處理完成時間、爭議案件補件率及車況紀錄完整率。

## 八、落地評估

### 8.1 技術可行性

目前所需能力都有成熟的技術基礎，包括手機相機串流、影像品質判斷、車輛與內裝辨識、影像配對、異常偵測、雲端運算與 API 介接。主要挑戰不在單一技術是否存在，而在真實車型、光線、停車場環境與拍攝差異下，能否維持穩定準確度。

Prototype 已驗證主要操作概念與畫面流程；正式化仍需完成真實相機、模型服務、帳號權限、資料儲存、狀態同步與企業 API。

### 8.2 資料可行性

官方提供的流程資料與真實使用者照片足以支援前期資料盤點、品質分析及視角模型研究，但車損模型仍需要更明確的異常標註、同車前後配對與人工覆核結果。資料也必須依競賽規範、個資要求與企業授權使用。

### 8.3 系統整合可行性

InspectFlow 採 API-first 架構，可先作為獨立的車況分析服務接入現有流程，不要求一次替換整套 iRent 系統。導入前需確認：

- 訂單、車輛、取還車時間與位置資料的取得方式。
- 影像上傳、車輛狀態與索賠請求 API。
- 外部處理系統可回傳的狀態與完成結果。
- 公司對清潔、維修、停用、放行及索賠的權限規則。

### 8.4 營運可行性

正式產品不應直接改變 iRent 未公開的派工與合作廠商流程。較低風險的作法，是先讓 InspectFlow 提供標準化證據與人工確認入口，再由既有系統承接後續處理。這能降低教育、流程與組織調整成本。

### 8.5 風險與控制

| 風險 | 控制方式 |
| --- | --- |
| 不同車型與環境造成辨識不穩定 | 依車型與區域驗證，低信心轉人工 |
| 反光或陰影被誤認為損傷 | 手機端先做品質引導，多張影像交叉確認 |
| 缺少可比較的取車前影像 | 標示證據不足，使用歷史基準補充但不自動定責 |
| 使用者掃描時間過長 | 正常流程只做六區掃描，異常才補掃 |
| AI 誤判影響客戶權益 | 人工覆核、保留原圖與完整稽核紀錄 |
| 個資或非目標車牌進入影像 | 上傳前後進行遮罩、權限及保存期限管理 |
| 與現有營運流程不一致 | 透過 API 接入，先確認企業 SOP 再設定狀態規則 |

### 8.6 建議導入方式

1. **離線驗證**：整理官方資料、建立標註規則，先驗證影像品質與異常辨識能力。
2. **小規模試點**：選定少量車型與營運區域，由內部人員或受控使用者測試掃描流程。
3. **影子模式**：AI 只提供建議，不改變車輛狀態，與人工結果比較。
4. **人工確認上線**：營運人員確認後才能送出處理與索賠請求。
5. **逐步擴大**：達成可判讀率、誤報率與處理時間目標後，再擴充車型、區域與自動化程度。

## 九、目前 Prototype 與正式產品的界線

| 項目 | 目前 Prototype | 正式產品目標 |
| --- | --- | --- |
| 手機端 | Flutter App，以本機影片與時間軸模擬連續掃描 | 串接真實相機與手機端品質模型 |
| 掃描結果 | 固定腳本模擬六區完成、刮痕與後座髒污 | 依真實影像動態判斷與擷取 |
| 後台端 | React、TypeScript 與固定假資料呈現三個核心頁面 | 串接帳號、案件資料、影像與企業狀態 |
| AI 判讀 | 以預設結果展示使用流程 | 雲端模型實際產生 Finding 與信心 |
| 處理與索賠 | 模擬 API 請求及跨頁狀態變化 | 串接 iRent 既有營運與索賠系統 |
| 資料保存 | 本機展示資料 | 具備權限、稽核、加密與保存期限的正式資料服務 |

Prototype 的價值是先驗證使用者是否理解掃描指引、營運人員是否能快速完成判斷，以及三頁工作台是否符合決策需求。正式導入的下一步，才是以企業資料、現行流程與 API 將這套互動轉為真正可運作的服務。

## 十、總結

InspectFlow 的差異不在於單純增加一個車損辨識模型，而是重新設計從「怎麼拍」到「怎麼處理」的完整車況資料流程。手機端提高影像品質並降低使用者負擔，雲端 AI 負責整理前後差異與異常證據，後台讓營運人員保留最終決策，再以 API 接回 iRent 原有系統。

這種做法能在不取代現有營運架構的前提下，逐步提升照片可用性、人工審核效率、車況追溯能力與使用者信任，並為後續更成熟的模型與自動化建立可靠資料基礎。
