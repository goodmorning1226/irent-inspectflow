# iRent InspectFlow 後台端 Prototype 分階段實作計畫

最後更新：2026-10-10  
文件狀態：第 8 階段程式收斂與自動驗證已完成；瀏覽器視覺、鍵盤、尺寸矩陣及展示演練待補驗

## 1. 實作範圍與執行規則

本計畫只處理 React 後台端 Prototype。手機端已完成第 8 階段總驗證；後台實作完成並取得使用者確認前，不開始正式跨端串接、影片剪輯或真實服務整合。

後台原始分階段實作涵蓋完整營運閉環；第 8 階段完成後，依展示需求收斂為單一營運工作台。評審可見功能只保留「車況比對、清潔／維修任務分配、依嚴重度排序的索賠審查」三項，客服、派工、索賠與管理者不再拆成不同角色入口。完整稽核與狀態資料仍保留在底層，供未來正式產品擴充。

Prototype 使用 React、TypeScript 與 Vite 實作，全部資料來自本機 JSON、記憶體 store 或 Local Storage。不得在此階段建立正式後端服務、資料庫、登入、iRent API、地圖服務、AI 推論、派工求解器、通知服務或付款／索賠系統。

執行時遵守以下規則：

1. 只能依序進行第 1 至第 8 階段，不提前實作後續功能。
2. 每個階段都要等使用者明確指示，例如「實作第 1 階段」，才可以開始修改程式。
3. 每個階段完成後立即停止，回報變更檔案、可操作成果、驗證命令、驗證結果及已知限制，等待下一次指示。
4. 第 1 至第 7 階段只做格式化、ESLint 與 TypeScript 靜態檢查；只有資料轉換、狀態守門或稽核事件等靜態分析無法涵蓋的關鍵邏輯，才追加一個最小 Vitest。
5. 第 8 階段才執行後台端完整總驗證、視覺檢查、尺寸矩陣、鍵盤操作及展示演練。
6. 所有 AI 結論、信心、任務優先度、ETA、KPI 與風險分數均為固定假資料，畫面必須清楚顯示「Prototype 模擬結果」或「展示假資料」。
7. AI 只提供證據摘要與建議；人工覆核、車輛狀態、重新上線及索賠結論必須由人員操作確認。
8. AI 不得自動認定法律責任、賠償金額或索賠成立；證據不足、視角不可比及歷史基準不足必須保留為可見結果。
9. 後台可讀取與手機相同識別碼及假資料，但第 1 至第 8 階段不做即時跨端通訊。正式跨端階段另行規劃。

## 2. 技術與設計基線

### 2.1 建議技術組合

- React、TypeScript、Vite。
- React Router 管理頁面與案件深連結。
- Zustand 管理展示狀態；若實作時依賴成本不合理，可改用 React Context，但必須維持單一資料來源。
- Vitest 與 React Testing Library 執行資料邏輯及關鍵互動測試。
- 第 8 階段視環境使用 Playwright 或可用瀏覽器工具執行完整流程與視覺驗證。
- ESLint、TypeScript `tsc --noEmit` 與 Prettier 作為基本品質門檻。
- 本機 JSON、靜態影像、SVG 車身位置圖及假地圖；不串接外部服務。

### 2.2 視覺方向

後台主題延續「車況證據軌跡」，但不複製手機介面。版面以桌面營運工作台為主，讓人員能在同一視野理解案件脈絡、影像證據與下一步決策。

- **核心色彩**：iRent Red `#DD2525`、Ink `#252525`、Workspace Gray `#F3F4F6`、Success Green `#2F9E69`、Warning Orange `#F47A32`。
- **文字**：優先使用 Noto Sans TC、Microsoft JhengHei 與系統無襯線字型；數值及案件編號不另外使用裝飾性等寬字體。
- **框架**：左側主導覽、頂部案件／角色資訊、中間證據工作區、右側決策欄。
- **資訊密度**：列表與證據比較可高密度呈現；決策按鈕、限制與守門條件必須留有清楚間距。
- **狀態語彙**：紅色表示需立即處理，橘色表示待覆核或證據限制，綠色表示條件已滿足；不把不同嚴重度都畫成紅色。
- **互動原則**：不使用無意義漸層、浮動 KPI 卡片牆或大量進場動畫；動態只用於篩選結果、決策回饋、狀態轉換及稽核事件新增。

| 案例                 | 主要用途       | 後台結果                                         |

| S02 後座飲料污漬     | 清潔閉環主線   | 人工覆核、暫停出租、清潔任務、完工複檢、重新上線 |

| S07 左前車燈破裂     | 安全異常       | 車輛下線、優先維修、完工授權後重新上線           |

## 3. 驗證策略

### 3.1 第 1 至第 7 階段輕量驗證

原則上只執行：

```powershell
npm run format
npm run lint
npm run typecheck
```

- 第 1 階段另執行一次 `npm install` 與 `npm run build`，確認工程骨架成立。
- 只有 JSON schema、store reset、狀態守門、稽核事件或權限邏輯等無法由靜態分析判斷的關鍵功能，才追加一個最小目標測試。
- 第 1 至第 7 階段不製作完整驗證截圖、不跑所有瀏覽器尺寸、不重複演練全部情境。
- 某階段尚未具備完整流程時，只需把限制記錄在回報中，不用為了驗證提前實作後續頁面。

### 3.2 第 8 階段完整總驗證

第 8 階段一次完成：

- 全專案格式化、ESLint、TypeScript、Vitest 及 Production Build。
- 營運總覽、案件列表、證據比較、人工覆核、車輛狀態、建單、派工、完工、索賠與稽核的完整情境矩陣。
- S01 至 S07 的案例切換、展示重設及 Local Storage 版本清除。
- 主要尺寸 1024×768、1280×800、1440×900 與 1920×1080 的版面檢查。
- 列表鍵盤焦點、表單錯誤、對話框焦點、色彩對比、空狀態與長文溢位檢查。
- 返回、深連結重整、快速切換案例、重複操作及防止重複建單。
- 本機 JSON、靜態影像及 SVG 的離線載入檢查。
- 依 3 分鐘影片後台片段進行一次不中斷展示演練，記錄等待時間及操作順序。
- 產出 `prototype/backend/docs/stage8-validation-report.md`，列出結果、修正、限制與執行方式。

## 5. 第 1 階段：React 骨架與後台設計系統

**完成狀態：已於 2026-10-10 完成並通過階段輕量驗證及 Production Build。**

### 實作內容

- 建立 `prototype/backend/` React、TypeScript、Vite 專案。
- 建立 npm scripts：開發、格式化、Lint、TypeScript、測試及 Build。
- 建立 React Router 與頁面路徑骨架。
- 建立共用色彩、字型、間距、表格、按鈕、狀態標籤與表單樣式。
- 建立桌面 App Shell：左側導覽、頂部列、內容區、角色顯示及「Prototype 模擬結果」。
- 建立營運總覽佔位頁與未開放路由頁，不先填入完整案件功能。
- 建立錯誤邊界與無法識別路由頁。
- README 記錄安裝、啟動、Build 與目前限制。

### 暫不實作

- 正式案件資料、篩選、證據比較、人工覆核、任務、索賠或 Local Storage。
- 真實登入、權限驗證、API、地圖或通知。

### 輕量驗證

- `npm install`。
- 格式化異動檔案並執行 `npm run lint`、`npm run typecheck`、`npm run build`。
- 互動、尺寸矩陣及視覺快照留到第 8 階段。

### 完成門檻

專案可由 README 指令啟動，主要導覽可切換佔位路由，沒有 TypeScript 或 Build 錯誤。完成後停止並等待「實作第 2 階段」。

## 6. 第 2 階段：共用假資料、Store 與案例控制

**完成狀態：已於 2026-10-10 完成，並通過階段輕量驗證。**

### 實作內容

- 建立 Vehicle、Rental、InspectionSession、Finding、Case、Task、Worker、Assignment、VehicleStatusEvent 及 AuditEvent 型別。
- 在 `prototype/mock-data/` 建立 S01 至 S07 的本機 JSON，統一車號、訂單、時間、地點、區域與影像來源。
- 明確對應手機端 `INS-DEMO-001`、`ABC-1234`、左側刮痕與後座污漬資料。
- 建立 Zustand mock store：載入情境、查詢案件、更新狀態、重設資料及產生稽核事件。
- 加入版本化 Local Storage；資料版本不同或內容無效時回復預設案例。
- 建立隱藏或明確標示為展示用的案例切換器與「重設展示資料」。
- 建立資料限制文字，避免把假信心、ETA 或 KPI 誤認為實際企業資料。

### 暫不實作

- 案件列表、證據 UI、建單表單及索賠畫面。
- 手機與後台即時傳輸；本階段只共享識別碼與資料內容。

### 輕量驗證

- 格式化、ESLint 與 TypeScript 檢查。
- 僅為「S01–S07 載入、版本回復、重設後狀態一致」追加一個最小 Store 測試。

### 完成門檻

七個案例都能被 Store 穩定載入及重設，相同案例每次回到相同初始資料，且手機主線識別碼一致。完成後停止並等待「實作第 3 階段」。

## 7. 第 3 階段：營運總覽與案件佇列

**完成狀態：已於 2026-10-10 完成，並通過階段輕量驗證。**

### 實作內容

- 實作 B01 營運總覽：待覆核、暫停／下線車輛、即將逾期、預約風險與通知。
- 指標採可操作入口，不做只有數字的裝飾性 KPI 卡片；點擊後進入相應案件篩選。
- 實作 B02 案件列表：車號、異常類型、風險、信心、狀態、建立時間、期限及負責人。
- 建立狀態、異常類型、風險、地點與負責人篩選，以及車號／案件編號搜尋。
- 支援排序、空狀態、清除篩選及列表列點擊。
- 角色切換先影響可見入口與說明文字，不在此階段實作完整權限阻擋。
- 案件列可進入第 4 階段預留的案件詳情路由。

### 暫不實作

- Before／After 證據、覆核決策、任務建立與索賠結論。

### 輕量驗證

- 格式化、ESLint 與 TypeScript 檢查。
- 若篩選組合邏輯無法由靜態檢查涵蓋，追加一個最小篩選測試。

### 完成門檻

使用者能從營運總覽找到需要處理的案件，列表篩選、搜尋與空狀態一致，並能進入正確案件路由。完成後停止並等待「實作第 4 階段」。

## 8. 第 4 階段：案件詳情與證據工作台

**完成狀態：已於 2026-10-10 完成，並通過階段輕量驗證。**

### 實作內容

- 實作 B03 至 B06，採「左側案件脈絡、中間證據、右側摘要」三欄工作台。
- 顯示案件、遮罩會員資料、車輛、訂單、地點、取還車時間與目前處理軌跡。
- 實作同車同區域 Before／After 並排或拖曳比較，以及視角可比性標示。
- 顯示廣角、中央、左側、右側多角度影像；切換 Finding 時同步切換位置與影像。
- 顯示異常位置、類型、嚴重度、可能新增、固定信心與來源影像。
- 限制必須與結論同層顯示：歷史不足、視角不可比、髒污遮蔽及低信心不可藏在 Tooltip。
- 完成 S03 新刮痕、S04 強反光與 S05 基準不足三種證據表現。
- 支援影像放大、返回列表及案件深連結重整。

### 暫不實作

- 人工結論送出、車輛狀態變更、建單及索賠結案。

### 輕量驗證

- 格式化、ESLint 與 TypeScript 檢查。
- 影像比較互動、三欄尺寸與視覺快照留到第 8 階段。

### 完成門檻

案件頁能在沒有口頭補充下說明「與什麼歷史影像比較、看到什麼異常、有哪些限制及 AI 為何提出此建議」。完成後停止並等待「實作第 5 階段」。

## 9. 第 5 階段：人工覆核與車輛狀態

**完成狀態：已於 2026-10-10 完成，並通過階段輕量驗證。**

### 實作內容

- 實作 B07 人工覆核：確認異常、修正類型／嚴重度、證據不足、要求補件或退回。
- 所有人工結論必須填寫理由；缺少理由時提供明確欄位錯誤並阻止送出。
- 實作 B08 車輛狀態：READY、暫停出租、下線及待複檢。
- 分開顯示系統建議與人工最終決定，不讓 AI 直接變更車輛狀態。
- 每次覆核、修正及狀態變更都立即寫入 AuditEvent。
- S04 可確認為反光／非車損；S05 可標示證據不足並建立後續補件意圖。
- 變更完成後更新案件時間軸、負責人與下一步提示。

### 暫不實作

- 正式任務派工、完工影像與索賠候選結論。

### 輕量驗證

- 格式化、ESLint 與 TypeScript 檢查。
- 僅為「理由必填、狀態轉換、稽核事件追加」追加一個最小目標測試。

### 完成門檻

人員可以完成覆核或標示證據不足，系統建議不會越過人工控制點，且每次修改都有理由與稽核紀錄。完成後停止並等待「實作第 6 階段」。

## 10. 第 6 階段：任務、派工與完工複檢

### 實作內容

- 實作 B09 建立任務：依 Finding 建立清潔、巡檢或維修任務；索賠待審留在第 7 階段。
- 實作 B10 任務佇列與 B12 任務詳情：優先度、期限、預約風險、地點、技能、工具、進度及原始證據。
- 實作 B11 派工工作台：靜態地圖、工作人員技能、目前工作量、建議人選、ETA 與建議理由。
- 系統只提出預先計算的建議；人員可人工改派並填寫理由。
- 實作任務狀態：待派工、已指派、處理中、待複檢、完成及退回。
- 實作 B13 完工複檢：原異常、完工影像、同區域一致性、通過或退回補處理。
- 車輛重新上線守門：必要任務完成、完工影像通過及人工授權三者都成立才能切回 READY。
- 完成 S02 後座污漬主線；補充 S06 先清潔再判讀及 S07 安全異常下線維修。

### 暫不實作

- 索賠人工結論、管理 KPI 與完整稽核頁。

### 輕量驗證

- 格式化、ESLint 與 TypeScript 檢查。
- 僅為「防止重複建單、合法任務轉換、重新上線守門」追加一個最小目標測試。

### 完成門檻

S02 可從污損覆核一路完成建單、指派、處理、複檢與重新上線；未滿足條件時不能提前上線。完成後停止並等待「實作第 7 階段」。

### 實作完成紀錄（2026-10-10）

- 已完成 B09 至 B13：Finding 建單、任務佇列、靜態派工建議、任務詳情、完工影像複檢與 READY 守門。
- 系統建議只作為派工參考，人工改派必須填寫理由；任務僅能依合法狀態順序流轉。
- S02 已具備清潔、派工、處理、完工複檢、人工授權及重新上線完整閉環。

## 11. 第 7 階段：索賠、稽核、角色與展示成效

### 實作內容

- 實作 B14 索賠候選：取還車時間、Before／After、多角度、既有損傷、模型限制與案件處理紀錄。
- 實作 B15 人工索賠結論：證據足夠、證據不足、非本次新增或需要補件；理由必填。
- 索賠畫面不提供 AI 自動歸責或自動金額；若需要金額欄位，只能標示為人工輸入展示值。
- 實作 B16 稽核時間軸：模型摘要、人工修正、車況狀態、建單、派工、完工、索賠及重新上線。
- 實作 B17 管理與成效：拍攝品質、待覆核案件、任務 SLA 與處理結果，所有數值標示為展示假資料。
- 完成客服、營運、索賠與管理者角色切換；依角色改變可見導覽與可操作控制。
- 加入通知中心、逾期標記、快速切換案例及展示重設入口。
- 完成 S03 索賠候選主線，並確保結論立即寫入稽核時間軸。

### 暫不實作

- 真實身分驗證、正式 RBAC、安全稽核後端、外部通知或賠償計算。

### 輕量驗證

- 格式化、ESLint 與 TypeScript 檢查。
- 僅為「角色操作限制、索賠理由必填、稽核事件順序」追加一個最小目標測試。

### 完成門檻

S03 可從證據包進入人工索賠結論，角色權限與責任邊界清楚，全部變更可在稽核時間軸追溯。完成後停止並等待「實作第 8 階段」。

## 12. 第 8 階段：整合、視覺收斂與完整總驗證

### 實作內容

## 13. 每階段固定回報格式

每完成一個階段，使用以下格式回報：

```text
階段：第 N 階段／名稱
狀態：完成／部分完成／受阻

已完成：
- 可操作成果

變更：
- 主要檔案與用途

驗證：
- 執行命令
- 通過／失敗結果
- 若有執行最小目標測試，列出測試名稱；完整操作與尺寸矩陣集中於第 8 階段

限制：
- 尚未處理、刻意留待後續階段或環境限制

下一步：
- 等待使用者指示「實作第 N+1 階段」
```

第 1 至第 7 階段不需要產生完整驗證截圖或完整測試報告；所有人工流程、視覺、桌面尺寸與展示證據集中於第 8 階段。

## 14. 後台完成後的下一階段邊界

後台第 8 階段及使用者確認完成後，才另外規劃跨端整合。跨端階段可以選擇：

- 兩端只讀取相同案例 JSON，以案例編號形成一致故事；或
- 建立最小本機 Mock API，讓手機送出結果後由後台載入。

目前不預先決定跨端方式，也不在後台實作階段建立 API。選擇時應以三分鐘影片穩定性、離線展示與修改成本為優先。
