# iRent InspectFlow Prototype 實作計畫

最後更新：2026-10-10  
文件狀態：手機端第 8 階段已完成；後台端第 8 階段程式與自動驗證已完成，瀏覽器視覺及互動矩陣待補驗

## 1. 目的與交付範圍

Prototype 的工作不是驗證 AI 準確率，而是讓評審在不需要額外想像的情況下，看懂 InspectFlow 如何把一次取還車檢查轉換成可判讀的車況證據、可執行的營運任務，以及可追溯的索賠與完工紀錄。

本次實作分為兩個可操作介面：

1. **手機掃描端**：以 Flutter 製作，使用本機預錄影片與時間軸腳本模擬掃描及 AI 判讀。實際展示只完成車輛單側無損、同一側有損與車內掃描三種情境，不開啟相機，也不需要把正式產品的每個車身區域全部實作。
2. **後台處理端**：以 React、TypeScript 與 Vite 製作，採單一營運視角呈現車況比對、異常審核、處理中案件及正常車輛管理；處理與索賠以 API 請求形式交由既有系統承接。

兩端只使用固定圖片、JSON 假資料、計時器與預設按鈕模擬結果，不需要串接真實相機辨識、雲端推論、iRent API、登入權限、推播、地圖、導航或派工最佳化。所有模擬判讀畫面都必須顯示「Prototype 模擬結果」。

## 2. Prototype 完成定義

完成品必須讓展示者從手機端開始操作，並在後台看到同一輛車、同一次訂單及同一個異常的後續處理。手機掃描端以三條可重複播放的展示路徑為必要範圍；其他情境可只存在後台假資料，不要求另做掃描影片。

| 必做情境   | 手機端結果                                                                   | 後台端結果                       |
| ---------- | ---------------------------------------------------------------------------- | -------------------------------- |
| 單側無損   | 播放車輛左側掃描影片，依序顯示對準、品質鎖定、自動擷取與「未發現明顯異常」   | 車輛維持可出租，不建立即時任務   |
| 同一側有損 | 播放構圖相近的左側有損影片，在固定時間點框出疑似刮痕，接續近距離或多角度證據 | 建立索賠候選案件，由人員覆核責任 |
| 車內掃描   | 播放車內座椅與腳踏區影片，框選污漬或遺留物並完成擷取                         | 建立清潔任務，完工複檢後重新上線 |

正式產品仍維持六區導引掃描設計。依 2026-10-10 最新展示決策，Prototype 總覽的車頭、左側、車尾、右側、前座及後座六區初始均為待掃描，使用者由單一入口啟動連續掃描；影片必須實際呈現六個不同視角，區域之間以短暫走動過場銜接。取車檢查與完工複檢不再提供 Prototype 入口，改由簡報或口頭說明。

## 3. 整體展示架構

```text
Flutter 手機端
  車況照片頁 → 選擇展示案例 → 播放掃描素材 → 腳本化判讀／異常補掃
                                         → 檢查摘要與模擬上傳
                                              │
                                   共用 scenario_id 與假資料
                                              ▼
React 後台端
  案件佇列 → 證據覆核 → 車況與索賠決策 → 任務安排 → 完工複檢 → 重新上線
```

Prototype 可完全離線執行。兩端不必真的互傳資料，只要使用相同案例編號及內容，即可在展示影片中形成一致故事。若需要更自然的跨端效果，可讓兩端讀取同一份本機 JSON，或在後台提供「載入展示案例」按鈕。

手機端的「掃描」不是單純播放一段完成動畫，而是將預錄影片當成可控的相機串流。影片時間軸會驅動畫面上的品質提示、進度環、異常框、自動擷取及結果切換，因此評審仍能理解正式產品在每個時點會做什麼，同時避免現場拍攝的光線、對焦與操作失誤影響展示。

手機端採明確的直橫向分工。使用者在 iRent 車況總覽、六區選擇、摘要、上傳及完成結果中維持直向操作；進入車外、車內或完工複檢的實際掃描前，App 先提示「請將手機橫放」，再把掃描畫面鎖定為橫向。較寬的預覽區能同時容納車身／內裝輪廓、單一即時提示、品質狀態與區域進度，也更接近使用手機拍攝完整車側的自然姿勢。離開掃描後，App 必須恢復直向。

## 4. 視覺與互動方向

### 4.1 設計概念

介面主題定義為「車況證據軌跡」。手機端不另造一套獨立 App，而是以官方流程圖中的「檢查車輛狀況」頁為起點，保留置中說明與底部紅色主操作，但將功能標題改為「掃描」，並以車號、車型及空白六區俯視圖取代車輛示意圖。使用者按下「掃描車輛狀況」後會直接進入橫向連續掃描，不再經過獨立六區總覽。使用者仍會感覺自己正在完成 iRent 原本的還車程序，差別只在於「逐張拍照」被替換成「六區連續即時掃描」。後台端則把同一筆證據沿時間、車身位置與任務狀態展開。

### 4.2 官方流程與介面萃取

本節依 2026 年 10 月 10 日可取得的官方 iRent 小學堂頁面、頁面內嵌的官方教學影片，以及 iRent 官網取還車說明整理。官方教學素材可能早於目前 App 版本，而且影片中的手機畫面解析度有限，因此只把能穩定辨識的流程位置與介面結構列為設計依據；無法讀清楚的按鈕文字、影像格數與細部尺寸不視為現況事實，開發前仍需使用最新版 iRent App 實機確認。

**教學影片中可辨識的介面結構**

1. 車況／照片總覽頁採白色或淺灰底，頂部有頁面標題與導覽，主要內容呈現車況說明、車輛資訊或照片區，頁面底部使用一個醒目的紅色寬版主按鈕。
2. 拍攝時進入深色、近乎全螢幕的相機介面；頂部保留返回與標題，中間是相機預覽，底部附近排列照片縮圖或待拍位置，中央設有大型圓形快門。
3. 拍攝完成後，照片會回填為縮圖，使用者可繼續補拍或回到淺色表單／總覽頁，再由底部紅色按鈕推進流程。
4. 還車頁除了照片區，仍包含其他還車資訊與確認欄位；因此 InspectFlow 不應取代整張還車表單，只替換其中的影像取得元件。

### 4.4 手機端視覺規則

- **品牌層**：延續 iRent 的白色／淺灰主頁、深灰文字、紅色頂部或底部操作區及紅色主按鈕。Prototype 暫以 `#DD2525` 作為接近官方素材的品牌紅，正式版仍需取得官方 Design Token。
- **掃描層**：只有進入相機後才切換為橫向深色介面，使用車身／內裝輪廓、品質鎖定環與即時提示。青色只表示對準、品質達標與自動擷取，不作為整個 App 的主色。
- **狀態層**：橘色表示疑似異常或待補掃，紅色表示無法繼續或安全風險，綠色表示複檢通過；顏色必須搭配文字或圖示，不能單靠色彩傳意。
- **元件層**：直向總覽頁採既有表單節奏與底部寬版按鈕；橫向掃描頁採中央滿版影像、頂部導覽、側邊區域進度、中央引導框及不遮擋預覽的品質資訊。避免把 iRent 流程改造成與原 App 無關的儀表板風格。
- **文案層**：沿用「車況」「取車」「還車」「照片／影像」等使用者熟悉的名詞；AI、Finding、信心分數與索賠候選不在一般會員畫面曝光。

| Token         | 建議值    | 用途                                 |
| ------------- | --------- | ------------------------------------ |

| Surface       | `#F6F6F6` | iRent 行動端一般背景                 |

| Action Orange | `#F47A32` | 疑似異常與待補掃提醒                 |

### 4.6 互動原則

- 每個畫面只要求一個主要動作。
- 由直向流程進入掃描前顯示一次橫放手機提示；離開掃描後自動恢復直向，不要求使用者自行切回。
- 掃描時只顯示一項最優先調整，例如「請再靠近」。
- 每項新指令至少保留約 0.6 至 1.0 秒；同一動作若橫跨多個時間軸事件，沿用相同文字，避免短暫閃爍或連續跳字。
- 相同動作在各畫面使用一致名稱。
- 錯誤訊息說明下一步，不能只顯示「辨識失敗」。
- 模擬判讀使用 0.8 至 1.5 秒動畫，但不宣稱為實測延遲。
- 正常狀態保持低干擾；只有異常、待決策與安全風險使用橘色或紅色。

## 5. 手機掃描端

### 5.1 技術方式

- Flutter 單一 App。
- App 啟動與一般流程鎖定 `portraitUp`；進入掃描頁時允許 `landscapeLeft` 與 `landscapeRight`，離開掃描頁時恢復 `portraitUp`。方向控制集中在共用掃描 Scaffold，避免每個案例各自處理生命週期。
- Flutter Web 不保證能鎖定瀏覽器或裝置方向，因此 Web 展示以橫向 viewport 模擬掃描頁；Android／iOS 才執行實際方向切換。
- 不開啟真實相機；使用三組本機 MP4 或等效動畫素材模擬相機預覽：`exterior_clean`、`exterior_damage`、`interior_dirty`。
- 每段影片搭配一份時間軸腳本，依播放秒數切換 `ALIGNING`、`STABLE`、`CAPTURED`、`DETAIL_REQUIRED` 等狀態，並提供提示文字、進度值、異常框座標與擷取影格時間。
- 使用 Flutter 的影片播放器呈現素材；Overlay、品質環、框選與縮圖由 App 元件疊加，不能把 UI 預先燒錄進影片，以便後續調整文案與節奏。
- 使用 Riverpod、Provider 或簡單 ViewModel 保存流程狀態。
- 以影片播放時間為主要時鐘，必要時使用 `Timer` 模擬雲端判讀與上傳。
- 不要求相機權限；固定素材取代實際 Camera Plugin。
- 提供隱藏 Demo 控制面板，可立即切換無損、有損、車內案例，並支援重播與跳至異常；一般操作畫面不提供 Prototype 重設選項。
- 所有掃描結果固定由腳本輸出，不執行真正的影像模型；畫面需常駐或在結果區明確顯示「Prototype 模擬結果」。

本案優先採用「預錄或生成影片＋腳本化模型結果」，不建議為 Prototype 製作完整 3D 車輛模型。影片能保留真實材質、反光及移動感，實作成本較低；腳本則負責提供可重複的模型輸出。若找不到同車同角度的有損素材，可以只對有損案例使用合成影像、局部特效或生成影片，但應保持車型、顏色、背景與運鏡一致，避免前後比較看起來是兩輛不同的車。

建議的時間軸資料格式如下：

```json
{
  "scenario_id": "S03",
  "video": "exterior_damage.mp4",
  "events": [
    { "at_ms": 0, "state": "ALIGNING", "message": "請將左側車身放入框內" },
    {
      "at_ms": 1100,
      "state": "STABLE",
      "message": "請保持穩定",
      "quality": 0.82
    },
    { "at_ms": 1900, "state": "CAPTURED", "capture_frame_ms": 1850 },
    {
      "at_ms": 2500,
      "state": "DETAIL_REQUIRED",
      "bbox": [0.56, 0.48, 0.18, 0.12]
    }
  ]
}
```

`bbox` 使用 0 至 1 的相對座標，讓同一份腳本可配合不同手機尺寸。上例時間與品質值只是展示假資料，不代表實測效能。

### 5.2 資訊架構

```text
原 iRent 取車／還車流程
    ↓
車況照片頁（Prototype 預設起點）→ 六區可選總覽
                              ├─ 車頭／車尾／右側／前座 → 固定完成摘要
                              ├─ 左側 → 無損或有損影片 → 自動擷取／局部補掃
```

錄製展示影片時，手機端預設直接從官方還車流程中的車況照片位置開始，不必先展示另一個 InspectFlow 首頁。M04 六區全部以待掃描狀態開始，按下「開始全車掃描」後以同一段連續影片完成右側、車頭、左側、車尾、前座及後座；完成後才能查看各區摘要。區域之間需保留移動提示與可感知的影像過場。

### 5.4 掃描狀態機

```text
WAITING → ALIGNING → STABLE → CAPTURED → UPLOADED
              │                       │
              └─ 單一修正提示         └─ DETAIL_REQUIRED
                                           → CENTER → LEFT → RIGHT

任何狀態 → EVIDENCE_INSUFFICIENT → 重試或送人工覆核
```

狀態由影片時間軸與預設劇本推進，不分析真實影像。左側區域的結果由隱藏 Demo 控制器設定為 `exterior_clean` 或 `exterior_damage`，不把「無損／有損」做成使用者可見的區域選項；後座使用 `interior_dirty`。`evidence_insufficient` 可保留為後台假資料或日後擴充，不列入手機端驗收。反光只作為掃描品質調整原因，未排除前不得擷取或建立 Finding。

### 5.5 關鍵操作路徑

- **六區瀏覽**：M04 可依序點選六區；車頭、車尾、右側與前座進入 M04A 查看既有完成影像，再返回總覽。
- **單側無損**：Demo 控制器預先設為無損 → M04 選擇左側 → M06 → M08 → M09 → M16 → M17 → M18。
- **同一側有損**：Demo 控制器預先設為有損 → M04 選擇左側 → M06 → M08 → M09 → M10 → M11 → M12 → M13「異常持續可見」→ M16。
- **車內污損**：M04 選擇後座 → M14 播放素材並框出污損 → M16 → M17 → M18。
- **完工複檢**：M01 選擇完工複檢 → M19 查看原異常 → 同區域掃描 → M20。

### 5.6 手機端內容邊界

- 不向租車使用者顯示「你造成了損傷」。
- 不顯示賠償金額或索賠成立。
- 不宣稱模型準確率。
- 不把 1–2 秒寫成全車掃描時間。
- 不要求使用者在證據不足時無限重拍。

## 6. 後台處理端

### 6.1 技術方式

- React、TypeScript 與 Vite。
- React Router 管理頁面；Zustand 或單一 mock store 管理狀態。
- 本機 JSON 保存案件、Finding、處理請求、索賠請求、車況狀態及稽核紀錄。
- 按鈕模擬向既有處理系統及索賠系統送出 API 請求。
- 變更保存在記憶體或 Local Storage，並提供重設展示資料。
- 展示介面不提供角色切換，以單一營運工作台整合必要操作。

### 6.2 資訊架構

```text
營運工作台
├─ 異常審核 → 前後影像與異常摘要 → 放行或選擇處理方式
├─ 處理中案件 → API 請求清單與詳情 → 可補送索賠請求
└─ 車輛管理 → 正常可供租用車輛 → 送出清潔、維修、保養或停用請求
```

### 6.3 畫面清單

| ID  | 畫面         | 必須呈現的資訊與操作                                     |
| --- | ------------ | -------------------------------------------------------- |
| B01 | 車況比對清單 | 車號、異常類型、嚴重程度、狀態與查看入口                 |
| B02 | 車況比對詳情 | 還車後影像可切換比對本次取車前或上次還車，多角度影像、異常摘要與建議處理 |
| B03 | 處理中案件   | 每筆 API 處理請求的車號、事件、方式、位置、急迫性及狀態   |
| B04 | 處理案件詳情 | 問題影像、異常位置、處理方式、API 狀態及索賠請求操作      |
| B05 | 車輛管理     | 只列正常車輛，可送出清潔、維修、保養或單純停用請求        |

### 6.4 主要操作路徑

- **車況查看**：B01 選擇車輛 → B02 查看前後差異與建議處理。
- **異常處理**：B02 選擇「確認並發送處理請求」或「送出索賠請求並處理」→ 選擇清潔、維修、保養或單純停用 → 案件移至 B03。
- **正常車輛處理**：B05 選擇正常車輛 → 選擇處理方式 → 車輛離開正常清單並移至 B03。
- **補送索賠**：B03 清單或 B04 詳情送出索賠請求；已送出者顯示鎖定狀態，不重複送出。

### 6.5 後台互動細節

- 車況詳情以影像比對為主、摘要為輔，不呈現與展示決策無關的完整稽核欄位。
- 不展示人員、班表、任務 Queue、合作廠商或內部派工；正式流程由 iRent 既有系統決定。
- 索賠不設獨立頁面，只保存「未送出／已送出」狀態與證據包送出紀錄；AI 不自動判定責任或賠償金額。

## 10. 建議實作順序

本節只定義依賴關係，不代表時程。

## 13. 產品邊界

- 六區是目前設計假設，取得官方拍攝清單後再調整。
- 1–2 秒只代表單區已對準時的品質鎖定設計目標。
- 模型信心、時間、任務優先度及 KPI 都是假資料。
- AI 不自動決定法律責任或賠償金額。
- 歷史基準不足、視角不可比或低信心時保留「證據不足」。
- 髒污遮蔽可能損傷時，先清潔，再掃描相同區域。
- 正式產品仍需處理隱私遮罩、權限、影像保存及刪除；Prototype 使用去識別素材。
